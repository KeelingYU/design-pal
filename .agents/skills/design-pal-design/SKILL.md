# design-pal 设计工具

用户是不写代码的产品负责人。只讲业务：他会看到什么、要他决定什么；命令与文件路径只在他要看时给出。

所有操作通过 `node scripts/design.mjs <命令> … --json`（在本仓库根目录运行）。完整命令见该文件开头。设计草稿保存在 `drafts/`（不进 Git、不会公开）。

## 0. 每次开始

运行 `node scripts/design.mjs status --json`。有未完成的草稿时，先问用户「是否接着上次的「xx」继续」，是就按其进度（`step`）继续，否则开始新的。

## 1. 设计新颜色主题（在已有组件库下，只改配色）

1. **收集方向**：问清用在什么产品、想要的感觉；接受三种起步：
   - 一句描述；
   - 参考图或网址：素材只存到 `drafts/<编号>/references/`，**永远不要放进 `plugins/`**。网址打不开或需要登录时，请用户改发截图。在 Codex 中抓取网址需要联网，会请求用户批准。看不清或识别不出风格时，说明识别到了什么、缺什么，请用户补一句描述或换图。
   - 从已有颜色主题出发：`new --from <主题>`。
2. **建草稿**：`new --id <小写编号> --library <组件库> --name <中文名>`。
3. **配色方向**：设计 2～3 个明显不同的方向，每个包含完整的 `light`、`dark` 两套 14 色（键名：bg、surface、surface2、border、borderStrong、text、text2、text3、primary、primaryHover、onPrimary、success、warning、danger）和一句 `desc`、`name`。写成 JSON 数组文件（放在 `drafts/<编号>/`），运行 `directions --id … --file …`。返回里有对比度问题的，先按建议色修正后再给用户看。浏览器会打开方向页，请用户选择或混搭。
4. **选定**：`choose --id … --label A`；用户要混搭时，选最接近的方向再用 `update` 调整。
5. **修改循环**：`preview --id …` 打开草稿演示页（组件总览 + 3 个示例页，亮暗都有）。用户提出修改（「主色再深一点」），把改动写成 `{"light": {"primary": "#…"}}` 这样的 JSON，运行 `update --id … --file …`，再 `preview`，请用户刷新查看。
   - **只能改颜色**。用户要求改圆角、布局、字体、交互等，说明这属于组件库层面：第一期可以在具体项目里作为项目定制，或记下来留待第二期修改组件库本身。
   - **对比度不足**（`issues` 中未保留的项）：告诉用户哪里可能看不清，给出建议色。用户坚持保留时，用 `update --accept <key>` 记录（演示页会标注）。
6. **定稿**：用户说「定稿」时，和用户确认名称与一句简介，运行 `finalize --id … --desc …`。重名时请用户换名。定稿只生成待发布包，组件库本身不变。
7. **发布（公开，不可撤回）**：
   1. 运行 `publish --id …`（不带 `--confirm`），得到将公开的全部文件。
   2. 用业务语言告诉用户：将公开什么、组件库版本变为多少、公开后别人可以安装使用且撤回不彻底；请他明确同意。
   3. 用户同意后运行 `publish --id … --confirm`。在 Codex 中推送需要联网，会请求批准。
   4. 结果处理：
      - `blocked`：有不属于本次发布的内容或其他问题，说明原因，不要设法绕过。
      - `push-failed`：说明原因，稍后可重试（再次 `--confirm`），或用户放弃时运行 `abandon`。
      - `published`：告诉用户已发布；在项目里说「升级组件库」即可获得。
   - 用户说「先不发」：什么都不用做，草稿保留，组件库和版本号都不变。

## 2. 替换示例页

1. `page --id <编号> --library <组件库> --name <名称>`：会切换到草稿分支 `draft/<编号>`。
2. 在 `plugins/design-pal/libraries/<组件库>/patterns/` 中用组件库组件编写新页面（遵守该组件库的 `RULES.md`），在 `src/demo/main.tsx` 中替换对应的示例页入口；只改示例页相关文件。
3. `npm run build` 后打开 `plugins/design-pal/libraries/<组件库>/demo.html` 请用户查看，按意见修改；每轮改动提交到草稿分支（提交作者为仓库配置的隐藏邮箱）。
4. 用户满意后 `page-finalize --id … --note "示例页「设置」替换为「订单详情」"`，再按第 1 节第 7 步发布。

## 3. 规则

- 未经用户明确同意，绝不运行带 `--confirm` 的发布，也不直接 `git push`。
- 不把 `docs/`、`drafts/` 中的任何内容加入版本库。
- 发布完成后回到开发分支 `dev`，并确认 `main` 已合并进来。
