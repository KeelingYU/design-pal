# design-pal

design-pal 提供可被 Agent 完整复刻的网页组件库。每个**组件库**决定布局、组件形状、交互、动效、图标；其下的**颜色主题**只决定配色，并有亮/暗两种模式。

## 命令位置

所有操作通过插件自带的命令行完成。插件根目录是本 `SKILL.md` 所在目录的上两级（`<插件根>/skills/design-pal/SKILL.md`），命令为：

```bash
node <插件根>/bin/dp.mjs <命令> [参数] --json
```

下文用 `dp` 代指这条命令。加 `--json` 读取结构化结果；退出码 0 成功，1 需要用户处理（如冲突），2 前置条件不满足（看返回的 `error` 与 `message`）。

## 和用户沟通

- 用户多为不写代码的产品负责人：讲发生了什么、对产品有什么影响、需要用户决定什么；文件路径、命令只在用户要看时给出。
- 任何会改动项目文件的操作（应用、换颜色主题、升级）都要先说明将发生什么，得到同意再执行。
- 不删除、不覆盖用户的文件；`dp` 遇到冲突会停下，不要绕过它手工复制文件。

## 1. 查看组件库

用户说「查看 design-pal 组件库」「打开画廊」时：运行 `dp gallery`，告诉用户已在浏览器打开，并用一两句话介绍画廊里有哪些组件库。

## 2. 推荐并应用到项目

1. **了解产品**：先读项目的 README、需求文档、`package.json` 等弄清产品类型与使用者；仍不清楚就问用户一句「这个产品主要给谁用、做什么」。
2. **推荐**：运行 `dp list --json`，按各组件库的「适用说明」推荐一个组件库和一个颜色主题，用两三句话说明理由；建议用户先 `dp gallery` 看看。若没有合适的组件库，直说原因（例如「效率型适合后台工具，不适合儿童教育产品」），让用户决定是否仍然使用。
3. **确认后应用**：
   - `dp` 只在「Git 仓库且改动已全部提交」时工作，这样任何时候都能一键退回。如果项目还不是 Git 仓库或有未提交改动，向用户说明原因，征得同意后再初始化 Git 或提交存档。
   - 运行 `dp apply --project <项目根> --library <组件库> --theme <颜色主题> --json`。
   - `CONFLICT`：项目里已有同名文件，本次什么都没写。把冲突文件告诉用户，一起决定如何处理（例如改名自己的文件），不要删除用户文件。
4. **完成待办**：按返回的 `todos` 处理（例如给应用根元素加 `class="dp-app"`、入口引入样式、安装依赖失败时重装）。
5. **验证**：运行 `node design-pal/bin/check.mjs` 并确保项目能启动或构建。
6. **告诉用户**：用业务语言说明：用了哪个组件库和颜色主题；项目被识别成哪一类（返回的 `kind`：新建 React 基础工程、已有 React 项目、非 React 项目），与你对项目的了解不符时先停下告诉用户；项目里新增了组件库文件和一个 `design-pal` 文件夹（规则、演示页、定制记录、自查工具）；追加修改了哪些已有文件。建议用户提交存档；之后只需说功能需求。

应用后，项目 `AGENTS.md` 中的 design-pal 一节和 `design-pal/RULES.md` 就是开发界面的依据（Claude Code 通过 CLAUDE.md 的 `@AGENTS.md` 读取）。

## 3. 按组件库开发界面

- 先读 `design-pal/RULES.md`，按第 3 节找最接近的页面配方（示例代码在 `design-pal/patterns/`），外观与交互以 `design-pal/demo.html` 为准。
- 每次改完界面运行 `node design-pal/bin/check.mjs`，修正全部问题。
- 组件库里没有的组件：按 RULES.md 第 9 节补做，记入 `design-pal/overrides.md`「新增组件」，完成后告诉用户补了什么。

## 4. 项目定制（只影响本项目）

用户要求「这个项目里某处设计和组件库不一样」时（例如「按钮改成直角」）：

1. 直接修改项目里的组件库文件或样式（不要改 `design-pal/baseline/`）。
2. 在 `design-pal/overrides.md`「定制」一节记一行：日期｜改了什么｜原因｜涉及文件。
3. 运行自查；告诉用户这项定制只影响本项目，不会同步回组件库，以后升级时若与新版冲突会单独问他。

用户要求「改回组件库原样」时，才可撤销定制，并删去 overrides.md 中对应的行。`node design-pal/bin/check.mjs --diff` 可列出项目相对原版的全部实际改动，用来核对记录是否齐全。

## 5. 换颜色主题

1. 说明：只换配色，布局与交互不变。
2. 运行 `dp theme --project <项目根> --theme <颜色主题> --json`。
3. `THEME_CUSTOMIZED`：项目改过颜色文件。告诉用户直接切换会丢掉这些颜色定制，请他选择：保留定制（不切换），或放弃定制并切换（同意后加 `--force` 重跑）。
4. 完成后建议用户刷新页面查看，并提交存档。

## 6. 升级组件库

1. 用户说「升级组件库」时，先确保本机插件是最新：Claude Code 运行 `claude plugin marketplace update design-pal`，Codex 运行 `codex plugin marketplace upgrade`（需要联网，必要时请用户批准）。
2. 运行 `dp upgrade --project <项目根> --json`（不带 `--apply`，只出计划）。
   - `up-to-date`：告诉用户已是最新。`DOWNGRADE`：本机插件比项目用的版本旧，先更新插件。
3. **先说明新版改了什么**：转述 `changelog`；说明将更新几个文件、保留几处项目定制。
4. **冲突逐条问用户**：对每个 `conflicts` 项，用一两句话说明「新版改了什么」与「你的项目改了什么」（依据返回的 `library` 与 `project` 差异），请用户选择「保留我的定制」（ours）或「跟随新版」（theirs）。有冲突时 `dp` 不会写入任何文件。
5. 用户同意后执行：`dp upgrade --project <项目根> --apply --resolve <文件>=ours --resolve <文件>=theirs … --json`。
6. 处理 `todos`（如新增依赖需重新安装），运行自查与构建，告诉用户结果并建议提交存档。项目不会自动跟随新版，只有用户要求时才升级。

## 7. 其他情况

- **换组件库**：不自动执行。说明这等于重做界面布局与交互，评估受影响的页面范围后交给用户决定。
- **项目不是 React**：`dp apply` 只放入通用样式、规则和 `design-pal/reference.html`。按参考中的结构与类名编写，交互按「交互要求」自行实现；提醒用户交互一致性可能略低，以演示页比对为准。
- **用户要改组件库本身**（而非只改本项目）：说明这需要在 design-pal 仓库中修改并发布新版本，本项目随后可升级获得。
